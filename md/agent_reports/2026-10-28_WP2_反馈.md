## 2. 四类 Connector 的实测结果

实际读取原 `task2_1_prototype/artifacts/wp1_smoke_20261028/` 的全部 **2202 条**源协议记录；没有用自行构造的小样本替代完整验收。每条输出均通过冻结 Pydantic 模型与导出 JSON Schema，原载荷和 context 逐字段相等验证通过。

| 接入器 | 原批次有效输入 | 补充输入 | 输出说明 |
|---|---:|---:|---|
| RestApiConnector | REST_API 1 | 0 | 保留历史 POST 创建订单响应；独立测试另用真实 ERP/MES ASGI GET 路由读取订单与工单 |
| DatabaseConnector | SQLITE 1 | SQLITE 4 | 真实只读读取 inventory，并核对源记录；另读取当前 orders 1 行及独立组织参考表3行 |
| MqttConnector | MQTT 400 | 0 | 工单/工序事件、360条四路遥测、9图、8日志；实测保存的接收队列和实时 +/# 订阅 |
| OpcUaAndPlcConnector | OPC_UA 1440 + PLC_FRAME 360 | 0 | 四指标分别作为单点节点读取；PLC 18字节解码，校验地址/上下文与二进制文件偏移 |
| 合计 | **2202** | **4** | **2206 条有效 RawIngestMessage** |

输出按模态：structured_record **29**，timeseries_signal **2160**，image **9**，log_text **8**。2160条信号消息是360次采样在 MQTT 1条、OPC 4条、PLC 1条的多协议表示，并非2160次独立物理采样；WP3 应区分协议来源和事件重复观测。

源 demo_erp.sqlite3 与原练习库均未迁移或写入。组织节点来自批准的 config.hierarchy，写入输出目录新建的 organization_reference.sqlite3，再由同一个只读 DB 接入器读取，类型仍为 resource、context.resource_kind=organization。原 REST 订单是创建时的 pending；补充 DB 订单是本次读取时的 dispatched，不覆盖历史载荷。DB 快照时间是采集墙钟并有 timestamp_basis 标记，不伪称仿真状态事件时间。

**POSTGRESQL 分支也通过独立单测**：注入专用 DB-API 连接，执行 set_session(readonly=True, autocommit=False)，只读 SELECT、读取列名、rollback、关闭 cursor/connection，包括查询异常路径。测试采用受控 DB-API 替身，未连接真实 PostgreSQL 服务器；实际完整批次因此仍只有五种协议，六种协议枚举的覆盖来自完整批次加独立适配分支测试。需要实际部署时提供相容驱动工厂与 JSON 类型适配，不把 SQLite 查询计作 PostgreSQL 实测。

## 3. 隔离、幂等与数据完整性

- 正常 PLC bytes/hex 输入可还原四信号、control_cmd、heartbeat_seq；按原缩放系数重新编码与源18字节帧一致。时间和工单来自调用方调度上下文，帧里没有捏造工单字段。
- 主验收主动注入截断、CRC 错、未知地址、错误头部、错误功能码、错误长度共6条PLC帧，另注入1条错误PNG哈希引用；**7/7拒收且全部写入 rejected_messages.jsonl**，未进入正常流。这7条是单独的诊断样例，不是原2202条发生丢失。
- 单测另覆盖无效控制码、非十六进制输入、PLC二进制偏移不符/设备地址与上下文错配、图片缺失/父目录/绝对路径/UNC/流路径及伪PNG、缺调度上下文、枚举/时间/缺字段/多字段/NaN/Inf、OPC质量/节点/时间不符。
- 图片校验相对路径、解析后范围、文件存在、SHA-256、Pillow verify/load；原9张PNG通过。图片标签与原始日志逐字段保留；fault/fault_cleared及日志中0x84、CNC_01、OP20、WO023完整传递。
- 原2202条重复投递一次，**新增0条、duplicates=2202**。确定性身份由batch/source/protocol/channel/event_key或sequence组成；同身份不同内容以IDENTITY_CONFLICT拒收，不默默覆盖。

## 6. 留给WP3的十项接口约束

1. 输入唯一标准边界为 RawIngestMessage；固定8顶层字段，不把源transport_records或rejected_messages当作合法下游输入。SemanticObject仍恰好7字段，五类对象枚举不变。
2. 原载荷在 raw_payload.source_payload，旁边保留已解码/解包的可读取字段。REST读取body字段，DB读取row字段，MQTT保留原字段，OPC提供单指标及节点四字段，PLC提供四信号/control_cmd/heartbeat_seq等。保留来源才能做多模态合并。
3. 原raw_context逐字段保留，Connector新增的唯一命名空间为_ingest：batch_id/source_sequence/channel/source_timestamp/event_key/resolved_ids。不能用传输序号覆盖仿真context.sequence。
4. 工序必须携带工单；resolved_ids.process_instance_key为[工单,工序]；id_registry的process查询键含原work_order，legacy_ids保留原UUID。禁止把不同工单的同序号工序合并。
5. 标准timestamp已归一UTC；原时间拼写仍在_ingest。输出按到达顺序，乱序/同刻数据不自动排序。按clock/run_id/phase/sequence制定状态更新策略；补充DB快照为采集墙钟，不能与仿真分钟直接混算。
6. OPC单点、MQTT四通道、PLC定点值可能描述同次观测；不能将不同协议同秒数据误当三次独立实验。PLC存在定点量化，需使用原协议说明。control/injected_fault是生成信息，不代替诊断判据。
7. PNG为源批次相对路径，基目录在connector_summary.asset_root；下游移动产物须同步资产或显式指定可信根。synthetic_label是生成元数据，不是视觉模型识别结果。
8. 日志log_message、故障码、state_action已原样保留。WP3负责规则提取与状态融合；普通图片/INFO不能覆盖未解除fault，明确fault_cleared才可作为恢复证据。
9. 同会话幂等已保证；message_id可作为下游持久表唯一键。重复投递是None，拒收也是None，应结合session计数/diagnostics区分；不把错误诊断转语义对象。新的DB轮询应使用新event_key。
10. 调用入口为四类Connector、ingest_stream或CLI；字段/示例/限制详见[接入说明](../../task2_1_prototype/services/connector_service/README.md)。MQTT/OPC目前本地Mock，PostgreSQL无实网验收，故障传播与五类API不在WP2。启动WP3前先依据本报告和冻结契约核对当前源码，不读取项目索引。
