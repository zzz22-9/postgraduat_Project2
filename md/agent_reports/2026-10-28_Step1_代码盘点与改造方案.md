### 已有业务流的真实边界

1. `erp/app.py:create_app(database_path)` 支持注入测试数据库，创建订单由 `POST /orders` 完成；订单号自动生成为 `ORD-...`，不是用户输入自由编号。
2. `mes/service.py:dispatch` 创建工单与工序；分配设备、下达工单分别由 `assign`、`release` 完成。下发工单本身不自动分配设备、不自动启动仿真。
3. `simulation/inputs.py:source_snapshot` 读取现有工单与资源分配，`SimulationService` 为每批创建独立目录。
4. `simulation/engine.py:simulate` 用 SimPy 排队与虚拟时间；通过 MES 的开工、报工、返修和质检函数更新批次内 `mes.db`，不推进原 `data/erp.db`。
5. 旧仿真输出 `input.json / mapping.json / run.json / events.jsonl / summary.json / mes.db`。`mapping.json` 是来源编号映射，不是任务2.1语义映射服务。
6. 默认教学设备为 `E-ASM / E-QC / E-MOVE`，工序类别限制为 `assembly / inspection / transport`。`CNC_01` 是新演示配置，不能直接将旧组装设备或全部工序强制改名。

## 3. 契约差异与拟采用的处理方式

### 3.1 先固化可执行契约，再开始 WP1

规范第2节是 JSON 示例、字段表和枚举说明，尚没有 JSON Schema 文件。WP1 开始时先建立 Pydantic 模型及导出的 JSON Schema，作为 WP1—WP5 共用依赖；这是契约准备，不提前实现 WP2 服务。

- `RawIngestMessage` 固定8个顶层字段：`message_id, source_system, protocol, modality, timestamp, object_hint, raw_payload, raw_context`。
- `SemanticObject` **恰好7个**顶层字段：`object_id, object_type, domain, level, state, context, timestamp`；禁止额外顶层字段；类型/域/层级按规范枚举。
- `RelationEdge` 固定 `relation_id, source, relation, target, weight, timestamp, context`；关系名称沿用第2.4节；推理风险优先放状态与上下文，不随意增加关系枚举。
- 对缺字段、错枚举、额外字段、非法时间和非有限数值分别测试。不能只用同一模型生成数据再验证自身，还要断言精确字段集合、正常样本和反例。
- 来源、run_id、sequence、仿真时钟、规则依据、图片标签来源保存在 `raw_context/context` 或内部存储表，不新增第8个 SemanticObject 顶层字段。

### 3.2 已发现的具体不兼容

`unified_samples/store.py:snapshot` 虽含七个同名字段，但还返回 `scenario_id/raw_id/source_system/state_context` 等字段；`state` 是字符串，`timestamp` 是仿真时钟对象。对象类型采用 `Equipment/Process/WorkOrder/Order/Enterprise/Factory/Line`，关系为 `contains/has_work_order/processing` 等。它不能直接作为此次冻结契约的输出。

拟新增适配器，不迁移覆盖旧库：将状态转换为字典、对象类型转换为规范小写、上下文统一为 `factory/line/process/work_order/order`，关系转为明确的 `executes/belongs_to/maps_to` 等；旧样本只作为可选回放输入。

### 3.3 需显式写入契约说明的工程细节

| 问题 | 拟采用方案（尚未实施） |
|---|---|
| 规范允许 SQLite，但 protocol 示例仅列 POSTGRESQL 等 | 将 `SQLITE` 作为本地后端的显式补充值，写入契约说明与测试；保留原列举值。它是规范内部缺项的拟定解决方式，不能静默把 SQLite 标成 PostgreSQL，也不能声称该值已由原文枚举冻结 |
| 仿真分钟与 ISO-8601 字符串 | 新实验配置带时区的 `simulation_epoch`，`timestamp = epoch + sim_time_min × 60秒`；在上下文保留 clock、仿真秒和序号。历史回放使用明确声明的合成 epoch，不伪造历史采集时间 |

| 同时刻与多次运行 | 内部用 run/scenario、事件时间、sequence 排序与隔离；持久化对象ID冲突须拒绝或显式映射，不靠模糊字符串替换 |
| 多模态状态合并 | 逐字段合并，保存每模态来源；普通图片/INFO日志不能覆盖尚有效的 fault。乱序旧数据进入历史，不无条件覆盖最新状态；故障恢复需明确证据 |
| 图片结果 | V0.1 按规范允许的生成元数据/标签提取，标记为合成真值；不声称完成工业视觉识别 |

### 协议边界与 PLC 约定

- REST 通过现有 FastAPI 路由；SQLite 走真实查询。MQTT 使用发布/订阅内存队列 Mock；OPC UA 使用命名节点、值、状态码和时间戳模拟。两种模拟模式在上下文和汇报中明确标识，不冒充已连接工业现场。
- PLC协议是**本项目自定义仿真帧**，不是已知307实验室设备的真实协议。拟定义 `帧头 + 地址 + 功能码 + 数据长度 + 数据区 + 控制指令 + 心跳序号 + CRC16`，文档明确字节序、温度/振动/load定点缩放、rpm范围和校验覆盖区间。
- 接入器不仅把协议名写进 JSON；必须经历发布/订阅、节点读取或二进制打包/解析。错误帧应可演示且可诊断。
- PostgreSQL、Neo4j、真实MQTT连接为可选部署模式；本机必跑路径使用SQLite/NetworkX/Mock。Neo4j模式按规范设计真实适配，不把只写compose服务当作驱动已集成；未连服务器实测时标记未验证。
